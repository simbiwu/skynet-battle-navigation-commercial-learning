# 阶段学习总结：状态同步实操编写参考

> 本文整理帧同步课程讨论中形成的教学偏好、工程判断和待核实事项，供后续编写状态同步实操文档时参考。它是编写参考，不替代 LESSON_03_SPEC.md、ENGINEERING_DECISIONS.md、课程进度文件或仓库规则；如有冲突，以仓库规则和当前有效 Spec / Engineering Decision 为准。

## 1. 使用范围

状态同步实操是独立的网络战斗方案。可以借鉴本阶段确认的教学方式和商业实时战斗目标，但不要把帧同步的机制、代码路径或假设直接搬过去。开始编写前核对当前 Spec、工程决策和真实源码；对尚未落地的讨论方案，明确标记为设计方向或待验证项，不能写成现有能力。

本阶段约定的触发语是“按规则下一节”（“下一节”也表示继续当前课程）。它表示沿当前教学顺序继续，不表示跳到别的文件或模块。用户提出追问时，先把问题讲清楚，再按用户的下一步指示继续。

## 2. 教学组织方式

### 按实际执行顺序讲

先交代当前文件、类或函数的职责、调用者和可观察结果，再沿代码实际运行顺序说明输入如何进入、状态如何变化、结果如何产生。不要只说函数做什么后就跳到某个 helper；若关键逻辑跨多层调用，就逐层说明谁调用、传入什么、返回或提交什么。

### 给代码足够上下文

引用代码时标明仓库完整路径、类和函数。选择足以看出前后关系的完整函数或连续代码块，避免失去上下文的孤立语句。多层调用分块贴出实际实现并按执行顺序解释。代码与当前分支不一致时，先核实再引用。

### 补齐背景并算完例子

首次出现的 Skynet、帧同步/状态同步、寻路、占位、实体句柄、投射物等概念，先解释解决什么问题、属于哪一层，不假定读者已熟悉术语。

关键公式和算法从变量含义、单位、原始关系讲起，再逐步推导代码。用具体数值把例子完整算到结果，并说明边界、失败条件和状态影响。简化例子还要解释它与工程真实值的对应关系。

当当前实现与目标架构或成熟做法不一致时，指出差异、解释依据，并说清针对当前目标哪个做法正确。不要把“当前代码如此”自动等同于“架构上应该如此”。

## 3. 本阶段形成的架构判断

### 状态同步与帧同步分别设计

二者是不同的网络模型，应分别说明权威状态归属、客户端发送什么、服务器返回或广播什么、模拟时序、客户端快速响应、延迟/抖动/丢包/迟到消息处理、校正与恢复。状态同步实操不能仅把帧同步输入流程改名，也不能用一种方案代替另一种。

快速操作响应是实时战斗的基本体验要求，应从设计开始纳入。状态同步通常需要结合本地预测、服务器校正和远端插值等适用机制；最终采用的具体机制和合同以项目 Spec 与实现为准。

### Skynet Service 与游戏实体不是同一概念

一个玩家/连接由独立 Skynet Service 承载，是常见的 Actor 式组织方式。它不自动意味着每个游戏单位都要成为一个 Service，也不意味着 Battle 必须让每个实体独立推进权威状态。讲解时分别说明 Service、Lua State、Battle 所有权、Unit/实体数据的职责和生命周期。“集中推进”也不等于所有目标查找都可以全量线性扫描。

### 已知实体解析与附近对象筛选是不同问题

从已知目标 ID 找回特定实体，是身份解析问题；成熟实现应有能按稳定句柄/实例 ID 直接解析的实体存储或索引，并定义实体销毁、复用和过期句柄的处理。仅保存 ID 本身不会自动带来 O(1)。

按位置寻找附近候选目标则是空间查询/AOI 问题，不等同于已知目标解析。若当前课程不实现 AOI，应明确范围和限制；不要把线性扫描说成通用成熟方案，也不要擅自扩成 AOI 实施任务。

### 逻辑投射物、表现弹体与寻路要区分

寻路解决单位如何绕开不可通行区域到达目的地；直线、抛物线或追踪飞行的投射物通常按轨迹推进，不因“会移动”就成为 Navigation Agent。若障碍或单位碰撞会影响权威结果，服务器需要按玩法合同做连续轨迹碰撞/扫掠检测，并确定碰撞顺序、命中与阻挡规则。仅有客户端弹体表现或到达时触发逻辑，不能据此声称支持障碍阻挡。表现是否像素级一致，也不同于权威命中/伤害结果是否一致。

## 4. 帧同步讨论中的项目观察与纠偏

以下用于理解当前帧同步实现，不自动构成状态同步规格：

- 早期帧同步实操材料使用 50 ms 一帧（20 Tick/s）。用户明确认为这不应作为商业目标基线；本阶段提出并完成了向 60 Tick/s、固定约 16.67 ms 推进的工作。引用时仍须核对实际分支、Spec 与工程决策，并确认移动步长、冷却、投射物寿命、输入排程、回放和恢复等依赖 Tick 的逻辑一致更新。
- 当前示例 Bolt 的目标解析使用 std::find_if 遍历 Unit vector，是线性查找；多个 Bolt 时成本会累积。它可作为当前代码行为讲解，但不应被描述为规模化实体解析的理想方案。
- 已知目标解析应通过稳定实体句柄/索引；附近目标选择属于 AOI/空间查询。本阶段没有要求实现 AOI。
- 当前 Bolt 示例不会因为经过建筑而自动受阻；没有权威障碍轨迹检测，就不能说投射物已支持障碍阻挡。另有空中导航扩展方案文档，但除非实现与合同已经核实，不应写成可用能力。

引用这些内容前先确认仍与当前版本一致，并显式区分样例现状、设计目标和已验证实现。

## 5. 状态同步实操编写检查项

### 权威与消息合同

- 哪个 Battle/Server 组件拥有正式位置、路径、技能、命中、伤害、HP 和死亡状态？
- 客户端消息表达输入意图、操作请求还是状态结果？服务端如何校验、排序、去重、拒绝或回包？
- 广播/快照包含什么、以何种顺序和标识发送？实体身份、版本和生命周期如何识别？
- 哪些数据只是客户端表现，哪些是权威结果，可持久化、回放或恢复？

### 实时响应与校正

- 操作发出后客户端何时反馈？哪些反馈可预测，哪些必须等待服务器？
- 预测失败、服务器结果不同、实体已销毁或输入迟到时如何校正？
- 远端实体如何插值；快照不连续或暂时缺失时如何表现和恢复？
- 服务器模拟 Tick、网络发送频率、客户端渲染帧率分别是什么？不可把这些频率混为一个数字。

### 网络与失败路径

按当前架构合同说明延迟、抖动、乱序、丢包、重复、过期消息、断线重连及服务器重启/战斗恢复中适用的行为。明确本功能实际持有的状态、队列、快照或重放数据的容量边界、淘汰/拒绝策略、超时和资源释放。

### 可复现证据

教程应说明如何启动相关 Service、观察输入到权威结果的路径、对照客户端表现与服务器状态，并用正向及负向场景验证关键合同。只报告实际做过的静态检查、编译、测试或运行结果；代码阅读不能写成“测试通过”。

## 6. 不应默认的事情

- 不要默认状态同步每帧广播所有单位完整状态；应由实际带宽、可见性、优先级和合同决定。
- 不要默认客户端权威；Server 对正式战斗结果负责，Client 提交意图并负责本地表现。
- 不要默认提高服务器 Tick 就能解决所有延迟体验问题；模拟频率、网络发送、预测、校正和插值是相关但不同的设计点。
- 不要默认每个实体一个 Skynet Service，或所有实体必须在单个 Service 中按固定方式推进；先核对 Battle 所有权、并发边界和生命周期。
- 不要默认 Bolt/子弹需要导航寻路；先根据玩法合同判断是路径移动还是轨迹碰撞。
- 不要把候选方案、未实现能力或当前样例限制写成正式工程事实。

## 7. 后续维护

开始编写状态同步实操前，再读取对应 Lesson Spec、工程决策、课程路线、教学指南和受影响源码；如发生冲突，先按仓库优先级核实并在文档中记录。若用户或后续实现会话纠正了本总结中的结论，应更新本参考文档，避免旧讨论覆盖新合同。

## 8. 跨多轮辅导经验：可直接执行的讲解规则

以下不是对某一轮对话的记录，而是从多轮课程学习、技术追问和讲解纠正中归纳出的长期规则。后续编写状态同步实操和继续辅导时，应主动套用；具体技术结论仍以当前 Spec、工程决策和实际源码为准。

### 8.1 按课程顺序讲，先让读者知道“现在看什么”

- 每节先说本节要回答的问题、当前文件/函数的职责、入口由谁触发、输入来自哪里、结果会交给谁。读者应先知道正在读的代码处于完整流程的哪一步。
- 沿真实执行顺序讲，不能只说一个函数做什么，就突然跳到某个 helper 或另一个文件。跨多层时逐段建立“谁调用谁、传入什么、返回什么、结果在哪里继续使用”的关系。
- 尊重当前课程的章节和学习进度，不擅自跳到后面的 Runtime、Gateway、Binding 或其他课程。用户说“下一节”时，按已约定的学习顺序继续；中途追问先回答追问，再等待用户决定是否继续。
- 用户讨论课程外的通用技术问题时，先独立、完整回答问题本身，再说明与课程实现的关联。不要把所有问题强行限定在当前课程。

### 8.2 代码必须有来源和上下文

- 代码引用标明文件路径、类/函数，以及当前代码段的调用者和被调用者。使用用户能打开的 Windows 工作区路径；不要给 WSL /home 路径链接，也不要拿不同工作区的旧副本冒充当前版本。
- 不截取脱离上下文的单行代码。给足以看懂声明、参数、前后调用和结果去向的完整函数或连续代码块；多层跳转按执行顺序分块，明确每块之间如何衔接。避免为显得完整而粘贴无关的大段文件。
- 当一行代码依赖其他实现时，把实际实现逐层列出。例如 Lua require 如何得到模块、模块如何加载 native、CMake 如何生成可加载模块、哪个 luaopen 函数注册接口；不能把边界步骤当读者已知。
- 讲多返回值或状态提交时，先给函数 return 的顺序，再逐个对应调用处左侧变量，继续指出每个值后来在哪里消费、何时成为正式状态。只解释生成处还不够。

### 8.3 每个变量、名词和结果都要落地

- 首次出现的概念先说明是什么、当前为什么需要、属于哪一层；不要要求读者靠名字或旧记忆猜。
- 讲关键变量时交代其来源、具体含义、单位/取值范围、谁拥有它、在哪里被改变、后续谁读取。区分“本帧输入”“缓存中的输入”“候选状态”“成功后提交的状态”等容易混淆的对象。
- 如果变量名和实际含义容易产生误解，要明确指出命名问题，准确说明它保存的是什么、何时生效，并给出更贴切的命名建议；不要只替含糊的名字辩护。例如 next_last 只暂存本帧最终采用的移动方向，成功推进后写入 last_input；它不是下一帧 input，last_direction_after_frame 比 next_last 更清楚。讲解前先核实它保存的是完整输入、输入的派生字段，还是待提交状态。
- 区分玩家/连接、Battle 席位、单位实例 ID、Service handle、userdata/native handle 等不同身份；不要用相近词相互代替。
- 解释函数或代码效果时，用具体数值展示调用前是什么、执行中怎么算、调用后变成什么。若问的是输出值，就给出几个输入下输出的实际值，不要停留在抽象定义。
- 解释“何时发生”时，指出由哪个 Timer、消息、函数或调用者触发；解释“谁接收/处理”时，沿实际消息路径到最终 Handler，而不是只说发给了某个 Service。

### 8.4 例子要沿同一份数据走到底

- 先给完整、合法、具体的输入记录，再按源码顺序追踪它：入口身份校验、字段验证、缓存/状态落点、模拟消费、输出记录/广播或错误回包。每一步列出关键字段值。
- 对关键分支分别把例子做完，例如按时到达、未到达、迟到/目标已处理、显式中立输入。说明每一支是否写入缓存、服务器最后采用什么值、产生什么返回码或权威结果。
- 明确相似但不同的情况：没有收到消息与收到后被拒绝；客户端输入与服务器合成值；路径规划与实际移动；Server 权威结果与 Client 表现；表现弹体与逻辑投射物。
- 不要只举例子的前半段，或抛出“800 mm”“4 帧”“6 帧”等数字却不解释它的业务含义、比较对象和后续结果。例子必须算到结论，并说明是否是当前实现的真实值、假设值或简化值。

### 8.5 公式从“要求什么”开始，逐步推到代码

任何涉及时间、速度、距离、步长、坐标、半径、格数、比例、取整或成本的公式，先说明它要计算什么，再按以下顺序讲：

1. 逐个定义变量、单位、范围和边界；
2. 写出直观的原始关系；
3. 把实际数字代入原始关系，逐步算出结果；
4. 展示如何整理成代码使用的公式，并解释每次乘除、加减和取整；
5. 说明代码结果在哪使用，改变了什么行为。

时间单位应分步换算。例如先算“帧数 × 每帧秒数 = 秒”，再将秒换成毫秒，最后换到 Skynet 时钟粒度；不要在一个式子里混写帧/秒、毫秒/秒和时钟单位，也不要一上来只扔最终整数公式。整数向上取整式要解释它对应的“最小够用整数”关系，以及为什么有减一等边界项。

### 8.6 图表只为理解服务

- 复杂图不是完整性的证明。避免一张 Mermaid 图塞入多条并行流程、大量分支和交叉箭头；用户看不出数据从哪里来、在哪里汇合时，应改图。
- 消息到达和定时推进若是两条独立流程，分开画并标标题，只在处理本帧权威状态的位置汇合。分支直接写清判定函数和实际效果。
- 优先使用短步骤、简单时间线、输入/输出表或简短 ASCII 图。图必须配读图说明，并与紧邻的代码、文件路径、实际数据例子对应；必要时不用图，直接列清楚步骤。
- 坐标、方向、空间范围等图必须标起点、方向、边界和单位，并紧跟读图要点。

### 8.7 讨论架构时，分清现状、目标和正确做法

- 分别说明“当前代码实际做什么”“目标合同要求什么”“当前目标下哪个做法正确”。用户问架构取舍时给出判断依据，不因课程样例现状而把样例实现说成成熟服务端的通用做法。
- 例如集中推进与实体归属不是非此即彼：要说明谁持有权威状态、谁驱动 Tick、目标查找使用何种实体索引、AOI 解决什么不同问题。类似地，移动单位寻路、投射物轨迹碰撞、视觉表现和权威结算应各自按职责解释。
- 方案、已实施功能和已验证结果必须分开标注。讨论中的设想不能写成现有能力，代码审阅不能写成测试通过；讲历史决策时核对它是否已被后续实现或决定更新。

### 8.8 被指出讲解有问题时，要重组内容

用户反复指出跳跃、变量没讲全、公式看不懂、代码没上下文、例子讲一半或图无法阅读时，应承认具体缺陷并直接给出重新组织后的完整解释。不要辩解读者应该能懂，不要只道歉后重复原文，不要继续增加新术语或把一条公式拆成更多抽象说法。修正后的讲解应能让读者从入口、代码、示例值一路追到结果。
