# FlyWow 可选空中导航最小实施方案

状态：已按本文实施并完成本次验证，结果与限制见 [实施结果](FlyWow_可选空中导航实施结果.md)。本文保留原始设计与资源合同。
日期：2026-10-13。

## 1. 目标和交付边界

在现有 FlyWow Navigation 内完成可选的 2.5D 空中导航基础能力：按飞行高度避开地面建筑、悬空静态障碍和动态空中障碍；提供寻路、路径推进、移动复验与占位提交，以及可供弹丸应用调用的扫掠查询。

BMAP 继续使用 V1。使用现有 Navigation 模块、MapRegistry、NavigationContext、Lua 入口和统一构建产物。不开第二套导航注册表、Service 或独立 AirGrid 系统。

本次交付 FlyWow 基础 API、Unity 导出链路、独立接入示例、测试、Benchmark 和合同文档。Frame Core、Battle、技能、弹丸业务和第三课实操教程的应用修改留给后续课程任务；基础扫掠接口必须现在可测试、可调用。

空中能力按需启用：旧调用者不传空中资产时，静态空中障碍集合为空；动态障碍仍可注册。地形高度检查是显式查询策略，未启用时不自动由 BMAP 产生空中障碍。显式传入空中文件路径后，缺失、损坏或配对错误必须失败。

## 2. 审计结论与修正

现有 GridMap 只保存 BMAP 地表高度和地面标记，不能还原楼顶或悬空障碍。DynamicOccupancy 只有 XZ footprint，无法区分同一 XZ 上不同高度的对象。NavigationContext 当前 ground scratch 按地图格数分配，不能再为可选空中能力增加一份全图数组。

因此增加同一资产包内的可选二进制空中数据，保留现有 Registry，在现有 Context 内按需持有空中动态数据和有界查询 scratch。静态数据直接作为 GridMap 的可选不可变成员，由一次完整加载构造；旧构造入口保持兼容。无需新资产 Registry 或通用 Backend。

上版方案需要修正：
- 单独限制展开节点不足以限制密集障碍碰撞成本；所有候选遍历、格子访问和后处理共享查询预算。
- 旧候选目录只按 BMAP hash 命名；空中数据变化也必须改变资产包身份。
- 任意 Collider 的世界包围盒只能保守表达几何，不能声称精确保留模型通道。
- 固定高度的 XZ 寻路不等于自动升降的三维寻路，必须明确合同。

## 3. 几何和高度合同

本次 2.5D 模型是“XZ 格子 + 每格零到多个阻挡高度区间”。多个区间可表达地面建筑和悬空障碍之间的通道。静态区间采用闭区间，接触边界算阻挡；同格重叠区间合并，按高度排序。水平静态几何保守覆盖整格。

单位或查询体采用轴对齐盒：中心整数世界坐标，XZ 半宽 radius_mm，Y 半高 half_height_mm，均非负。radius_mm 的用途沿用导航通行尺寸；盒体模型在空中合同中明确，不能暗称圆柱精确碰撞。动态障碍也使用整数世界 AABB，支持不同高度和不同尺寸。

Unity 默认关闭空中导出，通过 NavigationMapRoot 的显式 LayerMask 选择专用导航阻挡体；优先让作者用若干 BoxCollider 描述阻挡体。其他 Collider 使用其世界 AABB 保守导出，导出报告提示可能扩大阻挡范围；不把渲染网格或所有 Collider 自动当障碍。旋转盒同样使用世界 AABB。需要保留拱洞等通道时使用多个作者定义的阻挡盒。本版的正确性和可达性以导出的区间模型为准。

浮点转毫米只发生在离线导出：下界向下取整，上界向上取整，明确世界坐标轴与溢出检查。覆盖格必须处理闭边界接触，不能在格线处漏障碍。

例：障碍区间 [0,10000] mm，飞行体半高 200 mm，中心 y=10100 仍阻挡，y=10201 才通过。悬空障碍 [8000,10000] 下方，中心 y=7000、半高 200 的对象可通过（其它条件成立时）。

寻路使用调用者指定的固定 flight_y_mm，只搜索 XZ，可横向绕开障碍。Move/Sweep 支持端点 Y 不同的连续扫掠，因此支持调用者控制的升降。基础库不自行选择爬升高度；需要自动升降搜索属于三维路径规划，不在本次 2.5D 合同内。路径保存规划高度与查询尺寸；改变高度或尺寸后必须重新验证连接段并按需重规划，不能继续信任旧路径。

## 4. 可选静态资产与发布

在现有发布包增加 map.airnav，采用自有 airnav 格式 V1，显式 little-endian 编解码，不直接 dump C++ struct。它是 Navigation 包的可选组成文件，不修改 BMAP 字节布局。

文件保存：magic、格式版本、header 大小、map_id/map_version、XZ 原点/格尺寸/宽高、配对 BMAP 的完整 SHA-256、记录数与区间数，以及按格索引排序的稀疏记录和连续区间数组。每条格记录含 cell_index、interval_offset/count；每个区间含 int64 min_y_mm/max_y_mm。Header 原点类型与现有 BMAP 合同一致。发布前在格式合同固定字段宽度、偏移、预留字段必须为零和最大长度，并提供 Unity/Native 共用 golden bytes 测试。

不从 height_mm 推断建筑；不借用 BMAP reserved/clearance/area。

加载时校验格式、尺寸算术、范围、排序、区间合法性、数量、文件精确长度、BMAP SHA-256 配对及 ID/版本/坐标一致性。失败不替换 Registry。SHA-256 只用于加载/发布，使用项目已有可用实现；没有时采用经过已知向量验证的最小实现，不引入大依赖、Runtime shell 或第二套 hash 规则。

Manifest 继续是离线发布/审查元数据，记录每文件 SHA-256、可选能力和 package_hash。Runtime 不读 JSON。完整包内容身份按确定顺序对“版本化域标记 + BMAP hash + 空中文件是否存在 + 存在时的 airnav hash”计算 SHA-256，不将包含自身 hash 的 Manifest 再参与计算。

旧无空中导出的包保持现有命名/兼容规则；新有空中包按 package_hash 命名。继续同文件系统 staging -> 校验全部文件 -> 原子目录 rename；幂等检查必须包括空中文件及 Manifest。同一 BMAP 配不同障碍得到不同包身份。加载后 GridMap 记录地面身份与空中身份，供调用者识别确定的资产快照。

load_map 保留原单路径调用，允许显式可选 airnav 路径；不自动猜测邻接文件。只有完整配对成功才锁内替换 map_id 当前快照；已有 Context 保留旧 shared_ptr，包含旧空中数据。部署者必须发布完整包，再调用加载入口。

## 5. 简洁接口和接入顺序

以下名称是目标合同；Native 新 API 按 lowerCamelCase、Lua 按 snake_case，保留已有稳定地面 API。使用现有世界坐标、handle、Path 及错误结果；Path 按类型标记地面/空中，阻止混用推进函数。

新增公开操作仅为：
- set_air_obstacle：按 handle 插入或更新 AABB，初始放置、外部障碍瞬时更新共用；成功才改变索引。调用者明确这是状态设置，不代表已经扫掠移动。
- remove_air_obstacle：释放 handle 和索引关联；不存在时幂等成功。
- find_air_path：Context、起终点/终点范围、飞行高度、查询体尺寸、可选自身 handle、查询策略 -> Path 或明确失败。范围模式沿用现有终点范围语义。
- move_air：自身已注册 handle、目标中心、策略 -> 完整扫掠复验通过后原子更新该对象体积/索引；失败保持旧状态。
- advance_air_path：自身 handle、Path、毫米步长、策略 -> 沿 Path 推进；复用 move_air 的碰撞与提交逻辑。
- sweep_air：Context、起终点、查询体尺寸、可选排除 handle、策略 -> clear 或首个接触结果；只读，不改占位。

策略仅覆盖本次必需语义：是否检查 BMAP 地表（启用时整个体积下界高于覆盖地面，按显式 clearance_mm 检查）；静态/动态障碍默认均检查；通过 exclude_handle 排除自身。高度上限由调用者端点约束负责，不在 FlyWow 写入 Battle 数值。扫掠必须提供首个命中类别和动态 handle（静态无需业务 ID），以及确定的接触位置或有理数段参数，避免浮点时间决定命中顺序。

标准用法：load_map -> 创建现有 Context -> 注册动态阻挡体 -> find_air_path -> 每次 advance_air_path。手动方向移动调用 move_air。弹丸类调用者将来逐帧 sweep_air，再由应用决定命中效果；本次用 Navigation 示例证明这条基础调用可用。

新增垂直尺寸通过公开具名查询体传入，由宿主已有配置提供；不在 FlyWow 新建兵种配置表。Lua 接口使用具名请求 record，API 失败沿用 nil,{code,message}；C++ 使用现有 NavResult。高频调用不 I/O、不 yield、不跨 Service 请求。

## 6. 算法、动态生命周期与一致性

静态查询按 XZ 桶查稀疏有序区间；动态按现有格尺寸建立 Context 私有稀疏空间桶，并保存 handle -> AABB 与桶关联。复用现有容器/占位实现中适用的底层能力，不能拿二维 ground entry rule 代替高度碰撞，也不复制地面业务回调。同一对象的 ground 与 air 索引只在调用方明确注册时存在，不隐式同步两个状态源。

扫掠：沿中心线按整数 supercover/DDA 遍历格子，并枚举体积水平扩张可能覆盖的桶，含格线与角点；静态格柱和动态 AABB 做 Minkowski 扩张后，以整数/有理数 slab 相交计算首个接触。只遍历扫掠覆盖桶，不扫描整张地图或全体障碍，不用离散采样避免漏过薄障碍。乘法/比较使用经过范围验证的宽中间值或无溢出的有理数比较；不能假定任意 int64 乘法安全。相同时间以静态先于动态、再按格索引/handle 固定排序。

Air A* 为八邻接 XZ 搜索：整数直行/斜行成本，固定邻居顺序、启发式和堆平局顺序。每条边使用同一完整体积检查，斜走不穿角；起点到首格中心、最后中心到终点也检查。无障碍时先检查直达段可直接返回。平滑与路径推进复用 sweep，平滑消耗同一查询预算；预算耗尽可保留已验证的未平滑路线，不把未经检查的捷径返回。

路径包含整数世界点、游标、规划尺寸/高度、资产快照身份，不借用查询 scratch，不拥有动态障碍的生命期。动态索引变化不让整个路径永久有效：每次移动重验实际段，阻挡返回明确结果，上层决定何时重规划。没有自动重试或每 Tick 自动 A*。

动态 set/move 先准备和校验全部新桶关联，再提交；失败、容量不足或预算耗尽必须保留旧对象和索引。禁止先删除旧 footprint 再发现无法插入。销毁 Context 一并释放障碍、索引和 scratch。

advance 按 stride 沿折线累计真实路段距离，避免每轴各走 stride；剩余不足时到达终点。整数取整规则固定并防止零步死循环。每段成功后提交，后续阻挡可保留已完成的合法部分，返回实际位置、游标和阻挡状态；文档明确这种部分推进语义。单次 move 始终全成或全不成。

Context 单 owner 顺序调用；共享静态图不变，无进程全局可变 scratch。动态改变需来自同一个 owner。两对象同时相向移动的时序与优先级由应用确定；本库复验每次已提交状态，不宣称解决多对象连续时间协同避让。

## 7. CPU 和内存硬边界

空中 scratch 按需创建、复用，不额外分配 O(map_cell_count) 数组；稀疏 touched-node 索引和 heap 都预留有界容量。旧 Context 现有 ground dense 内存单独如实报告，本次不趁机改写 ground 实现。

首版默认与硬上限固定为下表，属于本功能资源合同。Context 可用一个可选具名 air_limits record 调低，不能超过硬上限；未传且没有空中操作时不分配。不要新增配置文件/注册表。数字是初始保护上限，尚非性能实测保证；调整必须附 Benchmark 依据并更新合同。

|资源|默认/硬上限|
|---|---:|
|单次 A* 展开节点|4096|
|单次 touched/open 节点|8192|
|单次查询/推进桶访问次数（重复访问也计数）|8192|
|单次区间、候选、地形测试次数（重复也计数）|65536|
|返回路径点|4096|
|每 Context 动态对象|4096|
|每动态对象桶关联|256|
|每 Context 动态桶关联总数|262144|
|airnav 文件|32 MiB|
|静态总区间|1048576|
|单格静态区间|64|

计数在超额工作发生前检查。预算覆盖 A*、扫掠、起终点连接、地形检查、路径构造和推进；不得嵌套调用就重置预算。长扫掠、大体积、密集桶也必须受控，禁止扫描结束后才报告超额。动态变更预检同样有界。对退化哈希行为采取有界探测或排序结构，不把平均 O(1) 当最坏情况保证。

错误区分 SEARCH_BUDGET_EXCEEDED、QUERY_BUDGET_EXCEEDED、CAPACITY_EXCEEDED、NO_PATH、BLOCKED、资产/参数错误，并映射现有错误类型。预算耗尽不能伪装成 NO_PATH 或 clear。绑定结果转换只与有界结果大小成正比；分配失败捕获并返回稳定错误。

这些约束限制单次工作量，不保证特定毫秒耗时，也不限制调用方一 Tick 发起任意多次查询。应用需限制本帧寻路请求量并复用路径；这属于后续 Battle 接入职责，不能在 Native 内偷偷建队列、线程或调度器。

Benchmark 必须记录实际 CPU/编译模式、地图格尺寸与尺寸、对象/区间密度、路径长、p50/p95/p99/max、展开/测试计数和静态/Context 内存，覆盖开放直达、长绕行、不可达、密集动态与预算耗尽。不仅测成功小图。至少连续 10000 次热查询，说明加载/初始化是否计入。报告同机原 ground 基线，验证空中关闭时无新增热路径成本。不宣称满足某 Battle Tick 时间，直到有该宿主的并发 Battle 数/帧预算并实测。

## 8. 修改位置和实施顺序

唯一 FlyWow 编辑源：WSL 主仓库的 server/third_party/skynet-flywow。其 Unity Package 源码也在该子模块修改；宿主 Unity 工程与正式生成资产按 WORKSPACE_WORKFLOW 在 Windows 处理。此任务不改独立 FlyWow 工作区。

1. 核对 WSL 当前源码与规则。发现不同于本文基线的已有能力先复用；不得覆盖用户修改。无代操作授权不运行 Git。
2. 在 navigation/native 增加空中格式/数据、查询及必要动态索引实现，扩展 GridMap/MapRegistry/NavigationContext/Path/错误，接入现有 CMake target。
3. 完成 navigation/unity 的可选 authoring、interval 导出、二进制读写校验、Manifest 和原子发布。
4. 扩展 navigation_binding.cpp 与 lualib/flywow_navigation.lua，提供最短完整示例。
5. 聚焦测试、Benchmark，更新 Navigation README/CONTRACT。修正宿主 BMAP 文档中“独立 Air Grid”旧约束，工程决策按现有编号追加可选资产组件合同；不修改无关课程结论。
6. 交付实际变更、构建/测试/性能证据、未验证项和后续课程接入说明。提交推送需另行授权。

## 9. 必须验证的完成条件

- BMAP V1 golden bytes 和原 ground 路径/占位回归不变；旧无 airnav 调用兼容。
- Unity -> airnav -> Native golden bytes；多区间、闭边界、负坐标、取整、溢出、错误 hash/截断/过大文件。
- 地面楼房横向绕行；高于建筑通过；悬空障碍上下通过；同 XZ 不同 Y 动态对象正确区分。
- 动态创建、更新、move、移除、Context 销毁；失败后旧索引完整，排除自身有效。
- 扫掠穿越薄障碍、斜走角点、大尺寸、多桶重复候选、首个命中和平局顺序；不能只测终点。
- Path 推进真实步长、部分成功语义、旧路线动态失效、高度改变复验及类型混用失败。
- 全部资源上限、病态密集候选、预算耗尽；不能返回假成功，所有内存均有 owner 和释放路径。
- 多 Context 隔离、多线程共享只读图、Registry 原子替换和旧 Context 保留旧完整资产。
- 重复相同查询/更新序列输出与预算结果一致；Lua 错误返回、生命周期、异常边界。
- 原子发布失败不留半包；同 BMAP 不同 airnav 包身份不同；显式错误文件失败、不传文件为空。
- 实际构建受影响 FlyWow target；运行 Native/Lua/导出测试及 Benchmark。Unity Editor 不可用时明确标注导出端未验证，不能宣布整个链路完成。

功能完整以本文明确的 2.5D 区间/体积合同为准。几何精度、固定高度规划和预算中止均是公开合同；不能通过省略动态障碍、扫掠、发布配对或资源边界缩减实现。
