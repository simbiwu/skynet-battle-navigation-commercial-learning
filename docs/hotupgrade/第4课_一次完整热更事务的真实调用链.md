## 从 Sample 的启动函数开始

本课沿一个案例走到底：由 first_service_handle 标识的现存 PlayerService 起初运行 V1；发布后仍是同一个 Service 实例、handle 和 Lua State，但普通模块导出、私有状态字段和 business.load 已更新。Sample 随后创建 second_service_handle，验证新实例从正式文件直接启动为 V2。

这些对象不能混为一谈。Service 实例是 Skynet 管理的运行单元；handle 是发消息时使用的地址；Lua State 是该 Service 执行 Lua 并持有模块缓存、闭包和私有表的环境。V1/V2 指代码版本，不是实例别名。Patch 是候选输入；部署后的 .lua 是后续新实例读取的宿主文件。

Sample Service 由 run_hotupgrade_sample.sh 配置启动。skynet.start 的回调运行后，run_sample() 在 Sample Service 自己的 Lua State 内执行；它不是由 Controller 启动，也不是管理 RPC 直接调用的 Lua 函数。

源码：FlyWow 的 [sample 启动回调](https://github.com/simbiwu/SKYNET-FLYWOW/blob/8e1424afedc5835bdbf4cc67244a6f272a0b2cbc/hotupgrade/sample/flywow_hotupgrade_sample.lua#L142-L152)、[运行脚本](https://github.com/simbiwu/SKYNET-FLYWOW/blob/8e1424afedc5835bdbf4cc67244a6f272a0b2cbc/hotupgrade/sample/run_hotupgrade_sample.sh) 和 hotupgrade/sample/skynet_config.lua。

run_sample() 先取得并初始化唯一 Controller，再创建第一个 PlayerService。以下是主线函数的完整实现。后面会从 create_player() 沿调用进入目标 Service。

来源：FlyWow hotupgrade/sample/flywow_hotupgrade_sample.lua 的 run_sample()；它由同文件末尾的 skynet.start 回调调用，当前仍在 Sample Service 的 Lua State。

~~~lua
local function run_sample()
    current_step = "获取并初始化 Controller"
    hotupgrade_service_handle = skynet.uniqueservice("flywow_hotupgrade_service")
    hotupgrade = require "flywow_hotupgrade"
    local sample_root = assert(os.getenv("HOTUPGRADE_SAMPLE_ROOT"))
    checked(skynet.call(hotupgrade_service_handle, "lua", "init",
        {patch_path = sample_root .. "/patches", root_path = sample_root .. "/host",
            service_path = "service"}), "初始化 Controller")

    current_step = "创建并登记 V1 PlayerService"
    local first_service_handle = create_player()
    local before = read_player(first_service_handle)
    print_player("V1", before)
    assert(before.service_handle == first_service_handle and before.equip == "刀" and before.schema_version == 1)
    assert(before.module_version == "v1" and before.load_attack == 105)
    assert(before.state_root_identity and before.module_root_identity and before.module_alias_identity)

    current_step = "发布 V2：由 begin 异步完成运行时更新与文件部署"
    local begun = checked(skynet.call(hotupgrade_service_handle, "hotupgrade", "begin", {path = "v2"}), "begin")
    print("已接受发布批次 " .. begun.batch_id)
    local completed = wait_for_completion(begun.batch_id)
    assert(completed.record.phase == "COMPLETED")
    print("原 PlayerService 批次 COMPLETED")

    current_step = "验收原 PlayerService"
    local after = read_player(first_service_handle)
    print_player("V2 existing", after)
    assert(after.service_handle == first_service_handle and after.state_root_identity)
    assert(after.module_identity == before.module_identity)
    assert(after.module_root_identity and after.module_alias_identity)
    assert(after.module_version == "v2" and after.equip == "剑" and after.schema_version == 2)
    assert(after.load_replaced and after.load_attack == 121 and after.cached_v1_load_attack == 100)
    assert(not after.patching)

    current_step = "创建并验收 V2 PlayerService"
    local second_service_handle = create_player()
    local created = read_player(second_service_handle)
    print_player("V2 new", created)
    assert(created.service_handle == second_service_handle and second_service_handle ~= first_service_handle)
    assert(created.module_version == "v2" and created.equip == "剑" and created.schema_version == 2)
    assert(created.load_attack == 121 and not created.patching)
    print("原实例与新实例业务版本一致：v2")
end
~~~

skynet.uniqueservice("flywow_hotupgrade_service") 是 Skynet 的同步创建/查询调用，会 yield 到 Service 管理侧返回 handle。require "flywow_hotupgrade" 加载业务侧公开 API；该模块顶层也取得同一个唯一 Controller handle，因此首次 require 必须发生在 Skynet 协程中。Sample 显式保留 hotupgrade_service_handle，用它发管理命令。

初始化通过 skynet.call(hotupgrade_service_handle, "lua", "init", ...) 发给 Controller Service 的 lua 协议。这里 init 是消息参数里的命令，不是直接调用 Controller 模块中的 Lua 函数。接收端在 [flywow_hotupgrade_service.lua](https://github.com/simbiwu/SKYNET-FLYWOW/blob/8e1424afedc5835bdbf4cc67244a6f272a0b2cbc/hotupgrade/service/flywow_hotupgrade_service.lua#L10-L28) 安装 skynet.dispatch("lua", ...)，再调用 hotupgrade_controller.initialize(controller_config)。成功后才固定 patch_path、宿主 root_path 和 service_path。Sample 随后才创建受管理业务 Service。

配置合同见 FlyWow 子模块 [docs/hotupgrade/README.md](https://github.com/simbiwu/SKYNET-FLYWOW/blob/8e1424afedc5835bdbf4cc67244a6f272a0b2cbc/docs/hotupgrade/README.md)。

### 从 create_player() 到真实登记

run_sample() 调用同文件的 create_player()，因为示例要求 Service 的创建和登记都经过 HotUpgrade 管理。hotupgrade.newservice() 将请求发给 Controller；Controller 先记录待创建项，再调用原生 skynet.newservice()。拿到真实 handle 后，Sample 向该 handle 发送业务 init RPC。

来源：FlyWow 同一 Sample 文件的 create_player()；调用者是 run_sample()。handle 是新 PlayerService 的地址。

~~~lua
local function create_player()
    local created, service_handle = pcall(hotupgrade.newservice, "player_service")
    if not created then
        error(tostring(service_handle))
    end

    local called, registered = pcall(skynet.call, service_handle, "lua", "init", {})
    if not called or type(registered) ~= "table" or not registered.ok then
        local cancelled = hotupgrade.cancel_service_creation(service_handle)
        if not cancelled.ok then
            error(tostring(registered and registered.code or "HU_PLAYER_INIT_FAILED") .. ": "
                .. tostring(registered and registered.message or registered or service_handle)
                .. "; cancel failed: " .. tostring(cancelled.code) .. ": " .. tostring(cancelled.message))
        end
        error(tostring(registered and registered.code or "HU_PLAYER_INIT_FAILED") .. ": "
            .. tostring(registered and registered.message or registered or service_handle))
    end

    return service_handle
end
~~~

skynet.call(service_handle, "lua", "init", {}) 中 lua 选择 Lua 协议；init 和空 table 是协议参数。调用发出请求并等待对端回包，调用方协程会挂起，然后在响应到达后继续。它不是直接调用 PlayerService 的局部 initialize()。

Skynet 1.8.0 的 skynet.call() 查找协议、打包消息、分配 session，再通过 yield_call() 等待；目标的 raw_dispatch_message() 调用协议 dispatch，参数顺序是 session、source、协议 unpack 的其余值。参见主仓库固定 Skynet 源码 [skynet.call](https://github.com/simbiwu/skynet-battle-navigation-commercial-learning/blob/583db5589f04d6cfef8bd8bdceece2f28e0870c7/server/third_party/skynet/lualib/skynet.lua#L725-L738)、[raw_dispatch_message](https://github.com/simbiwu/skynet-battle-navigation-commercial-learning/blob/583db5589f04d6cfef8bd8bdceece2f28e0870c7/server/third_party/skynet/lualib/skynet.lua#L901-L960) 和 [retpack](https://github.com/simbiwu/skynet-battle-navigation-commercial-learning/blob/583db5589f04d6cfef8bd8bdceece2f28e0870c7/server/third_party/skynet/lualib/skynet.lua#L761-L784)。skynet.send() 不等响应；主链路用 call 是因为每一步都要得到对端结果。skynet.fork() 创建并排队协程，但不会等待其完成；后面的 begin() 用它异步启动 run()。

PlayerService 在自己的 Service 中安装 skynet.dispatch("lua", ...)。收到 init 后，dispatch 分支普通调用本 State 中的 initialize()。V1 initialize() 通过 hotupgrade.require("player_logic") 加载模块，创建本实例私有 state 和 business，再调用 hotupgrade.register_service()。这几张表不发送给 Controller。

来源：FlyWow [host_v1/service/player_service.lua](https://github.com/simbiwu/SKYNET-FLYWOW/blob/8e1424afedc5835bdbf4cc67244a6f272a0b2cbc/hotupgrade/sample/host_v1/service/player_service.lua#L33-L103) 的 initialize() 与 skynet.start()。initialize() 由同一文件的 lua dispatch 收到 init 后调用；当前已跨 RPC 到 first PlayerService 的 Lua State。

~~~lua
local function initialize()
    logic = hotupgrade.require("player_logic")
    local version = logic.version()
    if version ~= "v1" and version ~= "v2" then
        return {ok = false, code = "HU_PLAYER_VERSION_UNSUPPORTED", message = tostring(version)}
    end

    local is_v2 = version == "v2"
    state =
    {
        equip = is_v2 and "剑" or "刀",
        level = 50,
        schema_version = is_v2 and 2 or 1,
    }
    state_root = state
    business = {load = logic.make_load(state)}
    cached_v1_load = business.load

    local registered_result = hotupgrade.register_service(
    {
        service_module = "player",
        service_update = {state = state, functions = business},
        before_upgrade = function()
            return business_queue(function() return true end)
        end,
        after_upgrade = function()
            return logic.version() == "v2" and state.equip == "剑"
                and state.schema_version == 2 and business.load(100) == 121
        end,
    })
    if registered_result.ok then
        registered = true
    end
    return registered_result
end

skynet.start(function()
    hotupgrade = require "flywow_hotupgrade"
    skynet.dispatch("lua", function(session, _source, command)
        local answer
        if command == "init" then
            if registered then
                answer = {ok = false, code = "HU_ALREADY_INITIALIZED", message = "PlayerService 已初始化"}
            else
                answer = initialize()
            end
        elseif not registered then
            answer = {ok = false, code = "HU_NOT_INITIALIZED", message = "PlayerService 尚未登记"}
        elseif command == "inspect" then
            if hotupgrade.patching then
                answer = {ok = false, code = "HU_UPGRADING"}
            else
                answer = {ok = true, player = business_queue(inspect)}
            end
        elseif command == "attack" then
            if hotupgrade.patching then
                answer = {ok = false, code = "HU_UPGRADING"}
            else
                answer = business_queue(function()
                    return {ok = true, attack = business.load(100)}
                end)
            end
        else
            answer = {ok = false, code = "HU_UNKNOWN_COMMAND", message = tostring(command)}
        end

        if session ~= 0 then
            skynet.retpack(answer)
        end
    end)
end)
~~~

V1 的 [player_logic.make_load(state)](https://github.com/simbiwu/SKYNET-FLYWOW/blob/8e1424afedc5835bdbf4cc67244a6f272a0b2cbc/hotupgrade/sample/host_v1/lualib/player_logic.lua#L1-L19) 返回捕获 state 的闭包；装备是“刀”时基础攻击增加 5，所以 business.load(100) 为 105。cached_v1_load 留住这个旧函数对象；普通模块导出更新不会自动替换业务代码缓存的函数引用。

业务代码传给 hotupgrade.require() 的原始名字是 player_logic；该入口根据实际文件路径将模块登记为 lualib.player_logic，并让 package.loaded.player_logic 与 package.loaded["lualib.player_logic"] 指向同一张导出表。Controller 收到的是规范名 lualib.player_logic，所以它能用 Patch 中的 lualib/player_logic.lua 匹配该模块。详见 [M.require()](https://github.com/simbiwu/SKYNET-FLYWOW/blob/8e1424afedc5835bdbf4cc67244a6f272a0b2cbc/hotupgrade/lualib/flywow_hotupgrade.lua#L411-L548)。register_service() 在 PlayerService 本地安装 hotupgrade 协议 dispatch，再通过该协议调用 Controller 的 register。跨 Service 只发送 service_module、已声明模块名、service_patch 能力等元数据；state、business 和回调留在目标 Lua State。Controller 用消息头的真实 source 作为 Service handle，并与受管理创建记录关联。登记成功后，create_player() 的 init RPC 才成功返回，Sample 将 handle 保存为 first_service_handle。

Sample 随后对 first_service_handle 发 inspect RPC。V1 返回 module_version=v1、装备“刀”、schema 1、攻击 105 和根表身份检查。此时 Controller 保存 handle 与模块名等元数据；模块根表、状态表、业务函数和闭包归 first PlayerService 持有。

## begin() 建立批次并等待生命周期屏障

现在 run_sample() 调用：

~~~lua
local begun = checked(skynet.call(hotupgrade_service_handle, "hotupgrade", "begin", {path = "v2"}), "begin")
~~~

这是 Sample Service 向 Controller Service 发出的 hotupgrade RPC。Controller Service 安装了同名协议处理器。dispatch 把参数交给 Controller 模块表的 control(command, request, source)；control() 根据命令普通调用 self:begin(request)。

dispatch 参数来自消息头和协议 unpack：session、真实 source，随后是 command、request。Controller Service 用 skynet.retpack(answer) 响应非零 session。Controller 再通过 step() 向业务 Service 发控制 RPC，这是另一条独立 RPC，不是管理命令原样转发。

Controller:begin() 检查没有活动批次或失败锁定，增加 sequence，建立 active 批次，令 Controller phase 为 WAITING_CREATIONS，然后用 skynet.fork() 启动 self:run(batch, ...) 协程。fork 不等待 run()；begin() 立即返回 batch_id。因此 begin 成功只表示请求已接受，不代表业务或文件已经更新。

来源：FlyWow flywow_hotupgrade_controller.lua 的完整 M:begin()。调用者为 M:handle_command()；RPC 返回 Sample 后，run_sample() 才得到 begun.batch_id。

~~~lua
function M:begin(request)
    if self.phase == "FAILED_LOCKED" then
        return hotupgrade_result.failure("HU_DEPLOYMENT_BLOCKED", "上次发布尚未恢复")
    end
    if self.active then
        return hotupgrade_result.failure("HU_UPGRADE_BUSY", "已有发布屏障")
    end
    if request.dry_run ~= nil and type(request.dry_run) ~= "boolean" then
        return hotupgrade_result.failure("HU_INVALID_REQUEST", "dry_run 必须为布尔值")
    end
    local path = request.path
    local dry_run = request.dry_run
    self.sequence = self.sequence + 1
    self.active =
    {
        batch_id = tostring(skynet.self()) .. ":" .. self.sequence,
        sequence = self.sequence,
        phase = "WAITING_CREATIONS",
        results = {},
        targets = {},
        success = 0,
        failed = 0,
        target_count = 0,
    }
    self.phase = "WAITING_CREATIONS"
    local batch = self.active
    skynet.fork(function()
        self:run(batch, {path = path, dry_run = dry_run})
    end)
    return hotupgrade_result.success({batch_id = batch.batch_id})
end
~~~

batch_id 由 Controller handle 和递增序号组成；sequence 随目标控制请求传递，由业务 Service 用来拒绝迟到命令。

WAITING_CREATIONS 是生命周期屏障：Controller 等已开始的受管理 Service 创建/登记和首次受控模块加载完成，避免目标快照漏掉正在启动的对象。run() 在 creation_count 或 module_load_count 非零时登记 waiter，再调用 skynet.wait()；登记 waiter 到 wait 之间不 yield。完成回调会 wakeup 该 waiter，run() 恢复后重验活动批次和计数。计数归零后 advance_deployment() 将阶段改为 DEPLOYING 并唤醒 run()。

这与 Prepare 不同。生命周期屏障稳定 Controller 看见的目标集合；Prepare 在每个目标的 Lua State 中等待该 Service 的业务 queue 排空。前者不负责业务排空，后者不管理新 Service 创建。

Sample 用 begin() 返回的 batch_id 查询 status；Controller 只保留活动批次和最近终态批次，不提供无限历史记录。

## Controller 读取、冻结 Patch 并选出目标

run() 从生命周期屏障恢复后调用 advance_deployment()，再调用 self:load(request)。load() 复查在途计数及 recovery_required，要求相对 path，通过 build_patch() 调 Native 递归枚举选定目录下的 Lua 文件。

load_files() 排序路径，逐个读取源码，用 load(source, ..., "t", {}) 做语法编译，并保存这一批冻结源码。此处 Lua load() 只编译成 chunk，并不执行模块或 Service Patch。候选模块和 Service Patch 构建函数要在 Update 到达目标 Service 的 Lua State 后才执行。Controller 因此基于同一份冻结源码匹配目标和稍后提交。

build_patch() 根据配置 service_path 分类：

- service/player.patch 映射到 service_module=player，是仅供现存实例执行的一次性脚本，不部署为宿主 Lua 文件。
- lualib/player_logic.lua 按宿主根目录相对路径映射为规范登记名 lualib.player_logic；已登记时更新运行时模块，也作为正式文件部署。
- service/player_service.lua 是完整的新 Service 入口，只部署给之后启动的 Service，不是当前实例的 Service Patch。

load() 遍历 Controller 登记快照：普通模块匹配各 Service 声明的模块名，Service Patch 匹配 service_module。一个 service_module 可由多个 Service handle 登记，因此合法的多实例目标都可进入同一 batch。Service Patch 若没有已登记匹配目标，或匹配目标没有 service_update，整批在发目标 RPC 前失败。

正式发布时，run() 读取待部署 .lua 的旧文件内容作为恢复快照，并固定 batch.files、batch.targets 和 target_count，然后把 Controller phase 改成 APPLYING。之后若失败，文件和已参与目标进入恢复流程；全部 Update 与正式文件部署成功后，才越过发布决定。

源码导航：[load_files / build_patch](https://github.com/simbiwu/SKYNET-FLYWOW/blob/8e1424afedc5835bdbf4cc67244a6f272a0b2cbc/hotupgrade/lualib/flywow_hotupgrade_controller.lua#L29-L153)、[Controller:load](https://github.com/simbiwu/SKYNET-FLYWOW/blob/8e1424afedc5835bdbf4cc67244a6f272a0b2cbc/hotupgrade/lualib/flywow_hotupgrade_controller.lua#L534-L596)、[Controller:run](https://github.com/simbiwu/SKYNET-FLYWOW/blob/8e1424afedc5835bdbf4cc67244a6f272a0b2cbc/hotupgrade/lualib/flywow_hotupgrade_controller.lua#L624-L794)。这些函数在 Controller Service 的 Lua State 运行；Controller 能读 Native 文件结果和登记元数据，不能读取 PlayerService 的 Lua table。

## Prepare：控制 RPC 进入 first PlayerService

Controller 按 Service handle 排序目标，先对所有目标执行 prepare，再开始 update。step(batch, target, command) 构造控制请求，包含 batch_id 和 sequence；只有 update 才附加冻结模块源码和可选 service_source。它用 pcall(skynet.call, target.service_handle, "hotupgrade", ...) 等待业务 Service 回复。RPC 抛错或结果结构不符合合同，转换为 HU_RPC_FAILED。

来源：FlyWow flywow_hotupgrade_controller.lua 的完整 M:step()；调用者为 M:run() 的阶段循环。target.service_handle 来自真实 Service 登记 source。

~~~lua
function M:step(batch, target, command)
    local request =
    {
        batch_id = batch.batch_id,
        sequence = batch.sequence,
    }
    if command == "update" then
        request.modules = target.modules
        request.service_source = target.service_source
    end

    batch.control_started = true
    local ok, answer = pcall(skynet.call, target.service_handle, "hotupgrade", command, request)
    if not ok or type(answer) ~= "table" or type(answer.ok) ~= "boolean" then
        return hotupgrade_result.failure("HU_RPC_FAILED", tostring(answer), command)
    end

    if not answer.ok and target.service_entry_file then
        answer.message = target.service_entry_file .. ": " .. (answer.message or answer.code)
    end
    return answer
end
~~~

目标 Service 能收到 hotupgrade，是因为 Controller Service 与公开入口都注册同一 Skynet 协议；业务 State 在 register_service() 时安装自己的 hotupgrade dispatch。协议相同不表示共享 Lua State。

目标 dispatch 收到请求后，source 是消息头提供的 Controller handle；它普通调用本 State 闭包 control(command, request, source)。control 检查来源、登记、批次身份、sequence 与本地状态。

Prepare 分支新建 txn，保存到 module_state.active_transaction，然后将 hotupgrade.patching 设为 true，再调用保存在本 State 的 before_upgrade()。回调不会发送给 Controller；它在目标 Lua State 中运行，并允许 yield。

Sample 的 before_upgrade() 向业务 queue 排入空操作。Skynet [queue.lua](https://github.com/simbiwu/skynet-battle-navigation-commercial-learning/blob/583db5589f04d6cfef8bd8bdceece2f28e0870c7/server/third_party/skynet/lualib/skynet/queue.lua#L7-L35) 用 current_thread 串行执行任务，并在 f 完整返回后递减 ref、唤醒下一个等待者。若当前业务在 queue 函数内 yield，协程仍在这个调用区间；queue 不会把 yield 当成完成。空操作获得执行权并返回，表示此前队列任务都已退出。patching 先置 true，因此新 inspect/attack 直接返回 HU_UPGRADING，不加入业务队列。

queue 不是全 Service 暂停器：它只覆盖确实进入该 queue 的业务。脱离 queue 的 skynet.fork() 业务协程不在排空范围。Sample 的受控业务入口先检查 patching，再立即进入同一 queue。

Prepare 成功后，目标将 txn.phase 置为 QUIESCED，dispatch 通过 retpack 回包；Controller 的 skynet.call 恢复。Controller 收到成功结果之前，不会向该目标发送 Update。

## Update：同一目标内先 Stage，再 Activate

所有目标 Prepare 成功后，Controller 逐个发送 update。Sample 的 Update 同时携带完整 lualib/player_logic.lua 和 service/player.patch 源码。两者走同一 Update 控制 RPC，但职责不同：普通模块 Patch 替换该模块完整导出；Service Patch 迁移本地状态并替换指定的业务函数。

业务端 control() 要求 txn.phase 为 QUIESCED，并检查每个目标模块已登记，然后调用 hotupgrade_module_patch.stage()。Module Patch Engine 在该 Service Lua State 编译、执行完整候选模块，检查导出并保存旧字段；它暂不改写线上模块根表。

接着 stage_service() 执行 Service Patch chunk，取得构建函数并将现存 state 表传给它。构建函数返回 migrate 和 functions。migrate 接收独立旧状态快照，返回完整候选状态，不直接更改线上 state。functions.load 则捕获原 state 表。Stage 保存旧状态快照和即将替换的旧 business.load。此刻 txn.phase 为 STAGED；线上逻辑仍未安装，patching 仍为 true。

Activate 是 Update 内部同步提交，不是 Controller 的另一条 RPC。目标先执行 module_patch.commit()，在原 logic 导出根表上替换完整导出字段；然后原地写入候选 state 字段；再直接替换 business.load；最后调用 after_upgrade() 验证版本、装备、schema 和结果。若任一步失败，目标立即尝试本地组合 Abort 并把失败回报 Controller。

来源：FlyWow [业务端 control()](https://github.com/simbiwu/SKYNET-FLYWOW/blob/8e1424afedc5835bdbf4cc67244a6f272a0b2cbc/hotupgrade/lualib/flywow_hotupgrade.lua#L177-L315)、[stage_service()](https://github.com/simbiwu/SKYNET-FLYWOW/blob/8e1424afedc5835bdbf4cc67244a6f272a0b2cbc/hotupgrade/lualib/flywow_hotupgrade.lua#L128-L175) 和 [Module Patch Engine](https://github.com/simbiwu/SKYNET-FLYWOW/blob/8e1424afedc5835bdbf4cc67244a6f272a0b2cbc/hotupgrade/lualib/flywow_hotupgrade_module_patch.lua#L29-L240)。调用者是目标 Service 的 hotupgrade dispatch 闭包；所有状态提交都留在该 State。

| 对象 | Activate 前 | Activate 后 |
|---|---|---|
| PlayerService 实例、first_service_handle、Lua State | 运行 V1 | 身份不变 |
| 私有根表 state | equip=刀、schema_version=1 | 同一张根表；equip=剑、schema_version=2、level 仍为 50 |
| 普通模块变量 logic | V1 模块根表 | 原模块根表装入 V2 完整导出 |
| package.loaded 的原名及规范别名 | 都指向 logic | 仍指向同一根表 |
| business.load | V1 函数 | 直接换为 Service Patch 新函数，读取原 state |
| cached_v1_load | 旧 V1 函数引用 | 仍是旧闭包对象 |
| hotupgrade.patching | true | 仍为 true，等待文件部署和 Finish |

V1 的旧闭包仍读取原 state，但其函数体只在装备是刀时加 5。状态已经原地变为剑，所以 cached_v1_load(100) 返回 100。新 business.load 按 V2 公式得到 100 + 20 + 1 = 121。这说明根表身份保留，不代表函数身份也被替换；更新模块导出字段也不会改写业务自己缓存的函数引用。

## 回到 Controller：部署正式文件并 Finish

目标返回 Update 成功后，Controller 才继续部署文件。所有目标都完成 Prepare 和 Update 后，Native replace_file() 将完整 .lua 写入宿主 root_path；.patch 不属于 batch.files，不会复制为运行时 Lua 文件。待部署文件全部成功后，Controller 调用 skynet.cache.clear()。

运行时提交和磁盘发布处理不同对象：first PlayerService 的 Lua State 已显式安装 V2 模块、状态和函数；正式文件供之后创建的 Service 或后续加载使用。skynet.lua 将 skynet.cache 指向 skynet.codecache；固定 Skynet 的 LUA_CACHELIB 由改版 Lua 注册，clear() 最终清理按文件名缓存的 Lua chunk，再创建新的缓存 State。它不替代现存业务 State 的 package.loaded 更新，也不会把现存旧闭包变成新闭包。源码可对照 [skynet.cache 绑定](https://github.com/simbiwu/skynet-battle-navigation-commercial-learning/blob/583db5589f04d6cfef8bd8bdceece2f28e0870c7/server/third_party/skynet/lualib/skynet.lua#L47-L49)、[Lua cache.clear](https://github.com/simbiwu/skynet-battle-navigation-commercial-learning/blob/583db5589f04d6cfef8bd8bdceece2f28e0870c7/server/third_party/skynet/3rd/lua/lauxlib.c#L1138-L1146) 与 [按文件名加载/清理缓存](https://github.com/simbiwu/skynet-battle-navigation-commercial-learning/blob/583db5589f04d6cfef8bd8bdceece2f28e0870c7/server/third_party/skynet/3rd/lua/lauxlib.c#L1244-L1305)。

文件与全部 Update 成功后，Controller 将 batch.phase 设为 PUBLISH_DECIDED、batch.decided 设为 true，再逐个发 Finish。目标要求 txn.phase 为 ACTIVATED，调用 Module Patch Engine finish() 释放旧模块快照，清理本地事务并设 hotupgrade.patching=false。到这一步业务才重新开放。

Finish 不是再验证一次值。旧快照一旦释放，目标不能靠它们回到旧版本，因此 Finish 在部署之后。Finish 循环开始前已越过发布决定；Controller 按 handle 顺序逐个 Finish，所以较早完成 Finish 的目标可能先恢复业务，而后续目标仍在收尾。若目标 Finish 失败或结果未知，Controller 继续尝试其他目标的 Finish，报告 RECOVERY_REQUIRED 并锁定后续发布，不把已经完成 Finish、重新开放业务的目标整体回滚。

源码顺序：[Controller:run()](https://github.com/simbiwu/SKYNET-FLYWOW/blob/8e1424afedc5835bdbf4cc67244a6f272a0b2cbc/hotupgrade/lualib/flywow_hotupgrade_controller.lua#L624-L794) 的部署和 Finish 部分，再对照业务端 [control() 的 Finish 分支](https://github.com/simbiwu/SKYNET-FLYWOW/blob/8e1424afedc5835bdbf4cc67244a6f272a0b2cbc/hotupgrade/lualib/flywow_hotupgrade.lua#L299-L315)。这是协调发布批次，不承诺数据库式全局原子性。

Sample 通过 wait_for_completion(batch_id) 轮询 status。每次请求都带 begin() 返回的 batch_id；只有 record.phase 为 COMPLETED 才返回，失败终态会抛出批次错误。skynet.sleep(1) 让出一个 tick 后再查。随后 Sample 读取 first_service_handle，断言 handle、状态根表、模块根表保持身份，module_version=v2、装备为剑、schema 为 2、新函数为 121、旧闭包为 100 且 patching=false。

status 的 lifecycle.phase 描述全局创建/部署/失败门禁；record.phase 描述该 batch_id 的批次阶段。Sample 等的是后者的 COMPLETED，再通过业务 RPC 验证真实运行结果。

## 后续新建的 Service 为什么是 V2

first PlayerService 通过本地运行时更新。second_service_handle 对应另一个 Service 实例和另一 Lua State；它由同一个 create_player() 路径创建，但此时正式宿主文件已经是 V2。

新实例从部署后的 [V2 service/player_service.lua](https://github.com/simbiwu/SKYNET-FLYWOW/blob/8e1424afedc5835bdbf4cc67244a6f272a0b2cbc/hotupgrade/sample/patches/v2/service/player_service.lua#L1-L105) 启动，初始化时调用 hotupgrade.require("player_logic")，读到正式 V2 模块。它以剑和 schema 2 初始化，并由 V2 的 make_load() 生成新的业务闭包，load(100) 为 121。Controller 没有复制 first PlayerService 的 table 给它。

Sample 对 second_service_handle 发 inspect RPC，确认其 handle 与 first_service_handle 不同，但代码版本、装备、schema 和攻击值一致。这验证了现存实例内存更新和后续实例磁盘加载都收敛到 V2。

## 失败时由谁恢复什么

发布决定前，如果 Patch 检查、Prepare、Update、文件替换或缓存清理失败，Controller 进入统一恢复分支。已经替换的正式文件按逆序尝试写回旧源码，再清理代码缓存；之后按逆序向已经参与的 Service 发 Abort。每个目标在自己的 Lua State 中恢复 Service 状态、被替换的业务函数字段和普通模块导出。Controller 不直接接触业务 table。

Prepare 回调失败也要 Abort：目标事务与 patching=true 已建立，即使业务未确认排空，也要通过 Abort 清掉本地事务后才能重新开放。Stage 失败时候选尚未安装；此前已经成功 Update 的目标仍需恢复。Activate 中途出错时目标先本地组合恢复，Controller 随后继续对参与目标发 Abort；批次身份使重复收尾可识别。

如果文件恢复、缓存清理或任一 Service Abort 失败，Controller 保留错误并进入 FAILED_LOCKED。新发布和受管理的新 Service/首次模块加载会被门禁阻止。resolve_deployment() 不替宿主写文件，不向业务 Service 发恢复命令，也不强制开放业务；宿主先核对并完成文件、运行时版本收敛及必要缓存清理，再按实际状态显式确认。UNCHANGED 不能用于已发送目标控制命令的批次；文件或运行时曾改变时，须按收敛合同确认。

Finish 属于另一边界。Finish 开始前所有目标 Update 和文件部署均已成功，Controller 已记录 decided。此后目标 Finish 失败可能是远端没执行，也可能执行了但响应不确定；已开放的目标不回滚。Controller 尝试其余目标 Finish，将批次标记为 RECOVERY_REQUIRED 并保持 FAILED_LOCKED，等待宿主核实。恢复边界见 [Controller:run()](https://github.com/simbiwu/SKYNET-FLYWOW/blob/8e1424afedc5835bdbf4cc67244a6f272a0b2cbc/hotupgrade/lualib/flywow_hotupgrade_controller.lua#L680-L794)、[resolve_deployment()](https://github.com/simbiwu/SKYNET-FLYWOW/blob/8e1424afedc5835bdbf4cc67244a6f272a0b2cbc/hotupgrade/lualib/flywow_hotupgrade_controller.lua#L847-L875)、业务端 [abort()](https://github.com/simbiwu/SKYNET-FLYWOW/blob/8e1424afedc5835bdbf4cc67244a6f272a0b2cbc/hotupgrade/lualib/flywow_hotupgrade.lua#L100-L126) 与 Module Patch Engine 的 [abort()/finish()](https://github.com/simbiwu/SKYNET-FLYWOW/blob/8e1424afedc5835bdbf4cc67244a6f272a0b2cbc/hotupgrade/lualib/flywow_hotupgrade_module_patch.lua#L175-L240)。

| 时间点 | Controller | first PlayerService | 正式宿主文件 |
|---|---|---|---|
| 登记后、begin 前 | phase=IDLE，登记目标含 first_service_handle | V1，patching=false，刀/schema1，business.load 与 cached_v1_load 同一函数 | V1 |
| begin 已返回、等待排空 | active 有 batch_id，phase=WAITING_CREATIONS | 原样运行，尚未 Prepare | V1 |
| Prepare 完成 | phase=APPLYING，批次继续 | active_transaction 为 QUIESCED，patching=true，queue 已排空 | V1 |
| Stage 完成 | Controller 尚未决定发布 | txn.phase=STAGED；候选和旧快照在目标本地；线上仍是 V1 | V1 |
| Activate 完成 | 尚未越过发布决定 | txn.phase=ACTIVATED；根表身份不变，状态和模块内容是 V2；旧闭包仍在；patching=true | V1 |
| 文件部署、清缓存完成 | batch.decided=true，开始 Finish | 运行时 V2，业务仍暂停 | V2 |
| Finish 与验收完成 | record.phase=COMPLETED，Controller phase 也为 COMPLETED | 原实例恢复业务，新函数 121、旧闭包 100 | V2；second_service_handle 从 V2 启动 |

读完本课，应该能沿代码回答：begin 为什么先返回 batch_id；为什么生命周期屏障与业务安全点分开；Controller 为什么不能直接改 state；普通模块、Service Patch 和正式文件分别改什么；旧闭包为什么仍返回 100；以及为什么 Finish 失败后只报告并锁定，而不再整体回滚。

源码审计结果：按固定提交逐段核对真实调用关系、状态字段与 Sample 断言，没有发现有源码依据的实质缺陷。Finish 后报告故障并锁定、不整体回滚是明确实现合同，不作为缺陷报告。
